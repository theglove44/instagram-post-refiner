Findings

Medium Filter Injection Confidence 9/10 app/api/comments/route.js:42

Description The comments list endpoint builds a PostgREST .or() filter expression by interpolating the raw, unescaped search query parameter directly into the filter grammar. Unlike .eq()/.ilike(col, val) — which parameterize the value — .or() parses its string argument as a PostgREST expression. Reserved characters (, ( ) . :) in search break out of the intended ilike predicate and inject attacker-chosen filter logic. The route uses the service-role client (RLS bypassed), so the injected filter runs with full table privileges.
// app/api/comments/route.js:41-43
if (search) {
  query = query.or(`text.ilike.%${search}%,username.ilike.%${search}%`);
}
Exploit scenario Authenticated request GET /api/comments?search=foo,reply_status.eq.replied) closes the injected predicate group and appends conditions, altering the query's boolean logic — e.g. returning hidden comments the filter switch was meant to gate, or pivoting filters onto columns the endpoint never intended to expose. The parse error is reflected into the 500 response body (error.message), giving a syntax oracle to iteratively craft a working payload. Impact is query-semantic manipulation + schema probing within the single admin tier (not cross-tenant theft) — hence Medium.
Fix — Stop interpolating user input into .or(). Either run two parameterized .ilike() queries (the value form is safe) and merge, or escape PostgREST reserved chars before building the expression: 
// option A — value form is parameterized, no injection
const term = `%${search}%`;
query = query.ilike('text', term);  // + second query on username, merge

// option B — neutralize PostgREST grammar chars before interpolation
const safe = search.replace(/[,()*.":\\]/g, ' ');
query = query.or(`text.ilike.%${safe}%,username.ilike.%${safe}%`);

Medium Open Redirect Confidence 8/10 app/api/instagram/callback/route.js:11–27

Description buildRedirect() constructs every OAuth-callback redirect target from the client-supplied x-forwarded-host / x-forwarded-proto headers with no allowlist. Both headers are attacker-controllable at the HTTP layer. The path is fixed (/?instagram_…) but the scheme + host are attacker-chosen. The error and !code branches (lines 35-46) redirect before CSRF-state validation, so the redirect fires unauthenticated.
// app/api/instagram/callback/route.js:11-17
function buildRedirect(request, path) {
  const forwardedHost = request.headers.get('x-forwarded-host');
  const forwardedProto = request.headers.get('x-forwarded-proto') || 'https';
  if (forwardedHost) {
    return new URL(path, `${forwardedProto}://${forwardedHost}`);
  }
Exploit scenario Attacker sends a victim a link to https://insta.mjoln1r.com/api/instagram/callback?error=x through a path that injects request headers (direct origin access bypassing the Cloudflare Tunnel, a forgotten/misconfigured proxy hop, or any intermediary trusting client X-Forwarded-*), with X-Forwarded-Host: evil.example. The victim's browser follows the 307 to https://evil.example/?instagram_error=… — a phishing redirect that begins on the trusted host. Mitigating factor: Cloudflare Tunnel normally overwrites these headers, so in the deployed topology this is hard to reach from the public edge — hence Medium, not High. No token or secret travels in the redirect.
Fix — Don't trust request headers for redirect origin. Derive it solely from the server-controlled INSTAGRAM_REDIRECT_URI (already imported), or validate x-forwarded-host against an explicit hostname allowlist: 
// build redirects from the configured origin only
function buildRedirect(request, path) {
  const base = new URL(process.env.INSTAGRAM_REDIRECT_URI).origin;
  return new URL(path, base);
}

Areas Reviewed & Cleared

  • Webhook HMAC (POST /api/webhooks/instagram) — signature verified via crypto.timingSafeEqual before any parse/DB work; length-mismatch throw caught and failed-closed. Spoofing requires INSTAGRAM_APP_SECRET. Sound.
  • Middleware auth gate & matcher — '/((?!_next/static|_next/image|favicon.ico).*)' covers all 48 routes incl. every /api/cron/*. Only static assets + the (HMAC-protected) webhook are exempt. Missing CRON_SECRET fails closed (cronSecret && … guard). No bypass.
  • OAuth CSRF state — crypto.randomBytes(16), httpOnly cookie, strict !== compare with presence checks, cookie deleted after use. Correct.
  • Token handling & data exposure — access_token never returned to the browser or logged; account routes hand-pick fields. Service-role key (lib/supabase-server.js) has no NEXT_PUBLIC_ prefix and is imported only server-side. RLS migrations replace permissive USING(true) with USING(false) on instagram_accounts / engagement_counts.
  • Media upload / storage & XSS — storage keys built from validated /^\d+$/ post id + crypto.randomUUID() + mime-mapped extension (no file.name in path → no traversal); deletes operate on DB-looked-up paths, not client input. Zero unsafe sinks repo-wide (dangerouslySetInnerHTML, innerHTML, eval, new Function); all Instagram-derived strings render through auto-escaping JSX.
